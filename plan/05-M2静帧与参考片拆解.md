## 3. 参考片实测

`world.execute(me);` 同人 PV（B 站 Av117346878490933）

| 项 | 值 |
|---|---|
| 时长 | **211.87 s**（3:32） |
| 帧数 / 帧率 | 5085 帧 / 24 fps |
| 分辨率 | **852×480**（文件名写"4K"，实际是 480p，别被标题骗） |
| 构图 | 左侧频道栏 + 右侧聊天流，Discord 式 chrome |
| 运动量 | **极低**。绝大多数时间是打字机 + 消息追加，没有连续运动 |
| 高潮处理 | **整屏大字**（`942 AD`、`world.execute(me);`），不是画出来的东西 |
| 配色 | 每场一个主色，**整屏硬切**（蓝 → 品红 → 红），不是渐变 |

### 三条值得借

1. **整屏换色，不搞渐变。** 它每个段落是整屏换一个主色，切换瞬间完成。我们方案里"每轮 A 段色温 +8%"几乎看不出来；换成**整屏硬切主色**，信号强十倍，成本更低。
2. **最高潮用字，不用画。** 全片最强的两帧都是排版：`942 AD` 和标题本身。我们 B① 只有 18 秒，却是全曲最响（−16.5 dB）——现在被塞进 384 px 的 LCD 里，太浪费。
3. **近乎全黑 + 一个元素。** 参考片 176 s 那一帧几乎全空，只剩一个红点。这直接印证了我们 387 s 之后的做法——不是我们想多了，是这类片子确实这么收。

### 两条不能借

1. **聊天窗口 chrome。** 它成立是因为那首歌在唱一个 AI；我们的歌在唱山和告别。抄外壳等于把 1994 年塞进 2023 年的界面。
2. **整屏文字墙。** 194 s 那帧把歌词整段铺满，是它版式最弱的一帧。我们也别干。

## 4. 由此产生的一条改动建议（需要拍板）

> **把 B① 从"界面逐项点亮"改成整屏大字。**

现在 B① 的规划是 8 个镜头、界面元素一个个亮（吉他 / 铅笔 / 翅膀 / 空间）。但它是全曲最响的 18 秒，参考片也证明这种位置该用排版砸。

改法：B① 期间**左屏界面全部退到 6% 亮度**，四个词依次以 120–160 px 打在画面中央偏左，一词一拍，中间留黑。B② 回来时界面复原、开始过载。

这样 B① / B② 就变成"砸 → 残骸"的两级，而不是同一段演两遍。

**代价**：多一套版式（约 4 个镜头），但可以砍掉原来 8 个界面点亮的镜头，总量反而少。

## 5. 环境坑（重要，会再遇到）

- `tools/ffmpeg.exe` / `ffprobe.exe` **已损坏**：`-version` 直接 `0xC0000409`（栈溢出）。169 MB 的静态包别再信。
- 重新下的 ffmpeg 7.1 **能执行、不能读写文件**：`Permission denied`，写自己新建的文件也不行。疑似被本机安全软件（火绒）限制，关沙箱也一样。
- 解法：`pip install opencv-python-headless --target .vendor`，用 **OpenCV 自带解码**抽帧，完全绕开 ffmpeg 进程。已装好，可复现：

```bash
PYTHONPATH=F:/dafeiyu/lanhuacao-mv/.vendor \
  "C:/Users/RedStarCLH/AppData/Local/Programs/Python/Python313/python.exe" - <<'EOF'
import cv2
cap = cv2.VideoCapture(".scratch/ref/ref.mp4")
cap.set(cv2.CAP_PROP_POS_MSEC, 176000)
ok, fr = cap.read()
cv2.imwrite(".scratch/ref/one.png", fr)
EOF
```

- 参考片副本在 `.scratch/ref/ref.mp4`，联系表在 `.scratch/ref/contact.png`（12 帧，每 17.6 s 一张）。
- `.vendor/` 约 200 MB，属临时依赖，不进版本库。

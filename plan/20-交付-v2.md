`preview.py` 1300 行，里面是**已经做好的、已经出片验证过的**东西：落碟开场、逐格 CRT

| (a) 把 `preview.py` 改写成四区 | 要重做开场、填充、结尾、七个模块；**旧片从此不存在**，且无法回退 |

和 `preview.ending_frame()`——因为它们讲的是**机器**，而机器在新旧两套版式里都在。

## 5. 逐字精度走 B（plan/19 §5 第 3 项）—— 做完了

### 5.1 做法

`src/stems_flux.py` → `src/align_chars.py`

1. 用已有的 htdemucs 模型分离出**人声轨波形**（`data/audio/stems_wav/vocals.wav`）
2. 算**正谱通量**（spectral flux）：172.27 Hz，1024 点 FFT，256 hop。
   **为什么不用 RMS**：元音持续时 RMS 一直高，看不见音节起点；谱通量在**起音**处跳一下，
   然后在元音里衰减——这正是我们要的「onset」
3. 40 ms 移动平均后再取峰（原始谱通量是 513 个频点求和，172 Hz 下抖 ±3%，
   原始局部极大常常只是某个音节里最噪的那个 bin）
4. **网格约束的 DP**（`align_chars._pick`）：每个字只能在「均分基准 ±0.42 s」内移动，
   路径代价 = 偏离基准 + 起音强度 + **步长偏差**（相邻两字的间隔与理想间隔差多少）。
   步长项是**软代价不是过滤器**——真的唱得不均匀时必须允许不均匀，否则 DP 宁可失败也不肯说实话
5. DP 失败时退回贪心（单调、最近、最强起音）

### 5.2 怎么验证的（不是"跑通了"）

**A. 在真实人声波形上量起音抬升**（`vocals.wav` 里，字时刻处 25 ms 窗口的 RMS 相对前 25 ms 的抬升）：

| | 平均抬升 | 中位数 | 抬升 > 0 的比例 |
|---|---:|---:|---:|
| **实测对齐**（word_times_v2） | **+0.161** | +0.125 | **79.2 %** |
| 均分基线（word_times） | −0.005 | −0.006 | 48.2 % |

> 这是最硬的一条：均分时间落在**没有声音变化**的地方（抬升为负）；实测时间落在**声音真的起来**
> 的地方。

**B. 谱通量峰值命中率**：实测时间点中 **45.7 %** 本身就是平滑后谱通量的局部极大；
随机时间只有 **12.1 %**。落在所在句谱通量 **90 分位以上**的有 **35.4 %**。

**C. 无一行退回均分**：53 行全部用了实测 onset（`uniform lines: 0 / 53`）。

**D. 相对均分的位移**：平均 102 ms，单行最大 662 ms。
**这个数字大不是错**——它说明这一句的字在歌里本来就挤在一起或者拉得很开，
而均分把它抹平了。`out/align-report.md` 逐句列了位移。

### 5.3 产物

- `data/audio/vocals_flux.npy` + `.json`（172.27 Hz 的谱通量曲线）
- `data/word_times_v2.json`（53 行，514 字的实测时刻）
- `out/align-report.md`（逐句位移表）

### 5.4 一个必须说的坑

`scene.LINES` 里的 `t` 是 `LRC时间 + OFFSET - LEAD`（**早 0.06 s**，因为歌词要抢在
起音前面一点点），而对齐表是用 **LRC 原始时间**做 key 的。**两边差 0.06 s，
直接查表会全部落空，然后静默退回均分时间**——画面看起来完全正常，只是逐字精度根本没生效。
这个坑在 `scene4.py` 的注释里写明了（要同时减 `LEAD`、并剥掉口令和唱句前缀的字数）。

## 9. 一个方法论教训：不要把整个仓库塞进上下文

上一条会话（`session-f16d07d8-…`）在 turn 22 反复撞
`413 payload too large (18159239 bytes > 16777216 limit)`，然后被中止。
**根因不是模型笨，是上下文被工具输出撑爆了**：整份 `plan/`（180 KB）、全部源码
（216 KB）、几十张 PNG 的 base64、ffmpeg/渲染日志——每一次工具调用都把结果**完整**留在
上下文里，几百轮之后 18 MB 就到了。

**接手这类项目时的做法**：

1. **先定范围再读**。这次我只读了 `plan/19`、`plan/18`、`plan/14`、`plan/12`、`plan/11`、
   `plan/10`——**没有**读 `plan/00`–`17` 的全文（那 130 KB 完全够触发同样的问题）。
2. **大文件用 `grep` 定位，用 `read` 带 offset/limit 取片段**。`scene.py` 26 KB、
   `preview.py` 64 KB 都是分段读的。
3. **看图用 contact sheet**：20 张静帧拼成 1 张，一次 `read_image` 看全；需要细看再挑
   2–3 张单图。**20 张单图 = 20 份像素进上下文。**
4. **不把 stdout 全量回灌**。渲染进度这类输出让它进后台 job，用 `job_output` 取**尾几行**。
5. **把重活扔给后台 job**（分离音频、渲染全片），foreground 只做小步验证。

这条写进 `plan/20` 是因为**它比任何一条技术结论都更值钱**：这个项目已经因为这条教训
损失过整整一条会话。
